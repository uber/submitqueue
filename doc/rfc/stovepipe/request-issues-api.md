# Request issues API

`ListIssuesByRequestID` lists projected issue observations for one request. Callers supply a configured queue, canonical decimal request ID, page size, and opaque continuation. The API reads only the request summary and request-scoped issue summaries. It does not load operational requests, builds, build issues, or request history, and never repairs or backfills data.

Each observation contains its source build ID, task ID, optional unit ID, optional opaque repair ID, and historical novelty (`new`, `existing`, or empty for unknown). Empty units identify task-wide failures. Observations remain after recovery; this API does not return current open/closed status. `ListOpenIssues` remains the queue-wide view of currently open issues. Identical task/unit observations from different builds remain separate. The source build identifies this observation, not the first build where the issue appeared across requests.

## Projection sources and recovery

`RequestIssueSummaryStore` is keyed by queue, request, build, task, and unit. Its primary key supports bounded request-prefix pagination without secondary indexes or joins. Observation membership is immutable. The optional repair ID is merged under the projection's own optimistic version, independently of operational versions. Observation replay preserves existing repair associations; identical repairs are idempotent, and conflicting nonempty repair IDs are errors. A repair event can create the read row before observation materialization reaches it.

Build analysis projects membership after each durable observation write, including duplicate writes. Before detection or any early stop, it replays the build's accumulated observations through bounded source pages; a failed projection can therefore be repaired even if the detector later omits that issue or the build loses the request outcome. Analysis DLQ recovery repairs the same persisted observations before recording abandonment, without invoking the detector. Projection failures return errors for normal or DLQ retry before processing advances.

The request-log materializer projects repair associations from retained `fix_submitted` events, including duplicate-event retries. These events contain the request, build, task, unit, and repair IDs. Operational `BuildIssue.FixID` remains the repair-submission guard and is not the projection source for repair IDs. Repair selection and issue reconciliation never consult the read projection.

Issue tracking freezes novelty after accepting an open issue state and before advancing its cursor: the opening build is `new`, including reopening a previously closed issue; another build continuing that opening is `existing`. Repeated polling retains the original label. Primary retries and DLQ recovery repair classification from the accepted cursor state. Observations awaiting reconciliation, skipped builds, and historical observations without retained classification remain unknown. Classification and repair association merge independently under the projection CAS, preserve known values on empty-source replay, and reject conflicting known values. Later issue transitions do not change historical classifications.

This follows selective event sourcing: durable observation identities are retained facts, while repair associations have retained events. Rebuilding exclusively from logs is not required. `IssueLog` contains open/close transitions, so it cannot reconstruct repeated observations across builds; analysis-completion events retain counts rather than individual issues. No additional observation log or background consumer is introduced.

## Rollout and explicit rebuild

Apply `stovepipe/extension/storage/mysql/schema/request_issue_summary.sql` before deploying the new writers and reader. If this table already exists, add `novelty VARBINARY(16) NOT NULL DEFAULT ''` before deploying this version; `CREATE TABLE IF NOT EXISTS` does not alter existing tables. The table starts empty; previously completed requests need explicit population. With `STOVEPIPE_MYSQL_DSN` set to the source database connection string, run `./tool/bazel run //tool/stovepipe/rebuildrequestissues -- --queue=<queue> --request-id=<id>` for each selected request. The operation is safe to repeat and can run alongside writers.

The rebuild discovers builds from the selected request's retained log, copies membership from durable build observations, and replays retained repair-submission events. It preserves existing rows, repair associations, and novelty classifications and fails on conflicting associations. It does not invoke providers, submit repairs, change operational state, or delete read rows. Rebuilding into an empty table requires the underlying observations and request/build correlation to remain available; retained repair events are required to restore repair IDs. Missing historical evidence cannot be inferred from lifecycle transitions or counts. Novelty is retained directly in the read row at reconciliation time; it is not present in the observation identities or repair events. An empty-table rebuild therefore leaves novelty unknown rather than reconstructing classifications from current mutable issue state. API requests have no operational fallback.

## Pagination and consistency

Observations are ordered bytewise by build ID, task ID, then unit ID. Page size defaults to 50 and accepts 1 through 200. Each call reads one bounded primary-key range from the projection, with one extra row to determine whether a continuation exists. Tokens identify the last returned build/task/unit and are bound to the queue and request. A cursor selects a position within that request's range; it does not authorize loading another build. Page size can change between calls.

Pagination is live rather than a snapshot: newly projected observations before the cursor require refreshing the first page. Projection lag or an exhausted empty listing does not establish build success or complete issue coverage. Retention of request history does not remove existing observation summaries.

Invalid identifiers, unconfigured queues, invalid page sizes, and malformed or mismatched continuations return `InvalidArgument`. A missing request summary returns `NotFound`; a summary whose identity disagrees with the selection is an infrastructure consistency error. Storage failures fail the call without returning a partial page.
