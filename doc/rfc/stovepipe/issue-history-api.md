# Issue history API

Issue history scans accepted requests in descending acceptance-time order, reads their issue summaries, then retrieves the original events using each summary's task, unit, build, and event type. Omitting task and unit includes all issues in the queue; supplying a task selects its exact unit, with an empty unit selecting that task's task-wide issue. Events include task and unit IDs and follow ascending bytewise task/unit order within each request. Source request IDs come from acceptance mappings, so expired builds do not require extra reads or hide linked events. Original timestamps and opening-build references are preserved, not used to sort history.

The request-acceptance window is inclusive at the lower bound and exclusive at the upper bound. Omitted bounds resolve to zero and server now on the first page; responses expose the resolved bounds and continuations keep them fixed. Event pages default to 50, with a maximum of 200. Each call examines at most 200 requests and 200 issue summaries and may return an empty page with a continuation after missing projections or logs. Continuations can resume within a request. All scans use existing primary-key order; there is no timestamp sort, new projection, or migration.

Coverage is limited to retained acceptance mappings and the build currently referenced by each request's issue summary. Missing, incomplete, or older projections can omit events, including earlier builds from the same request. Empty results do not establish that an issue has no retained history. Pages are live, not snapshots: later reconciliation can change projections or add events behind a cursor, so restart the window to refresh coverage.
